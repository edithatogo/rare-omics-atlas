# Research operating procedure — Ponytail full

1. Read active track `spec.md` and `plan.md`; check repository state, issue/PR ownership and source truth. **Work within the currently authorised track; the owner has authorised continued implementation.**
2. Independently record public landing/download listings, actual transfer/content hash, research-use permission, redistribution/hosting conditions and institutional classification as separate statuses. Verify sample-level independence, tissue/platform, molecular diagnosis and assay controls before inference. Hold only the affected claim when a required gate is unresolved; public intake can proceed on affirmative source policy without private consent forms. Refer to `research/source-access-ethics.md`.
3. For **each analysis**, run and record N0/N1 *before execution* per [novelty/priority protocol](../research/novelty-priority-protocol.md): current published/early-online/preprint studies and new datasets, exact dataset or method overlap, clinical journal fit and justified priority. Freeze the scientific contrast, estimand, covariates, outcomes, negative controls, splits and provisional journal. A search not executed is a hold, not a negative finding.
4. Start with published validated methods and simplest baselines. Among suitable implementations use **Rust > Julia > Python > R**. Read the [candidate audit](../research/rust-candidate-audit.md); prefer existing CLIs/libraries and distinguish the runtime engine from its interface and test oracle.
5. Preserve stage-level scientific contracts (`research/backend-replacement-policy.md`). Compare exact inputs and algorithmic outputs, validate numerically, note resampling and leakage boundaries. A replacement must pass its scientific/consumer contract and have acceptable resource/deployment/maintenance cost. Rust is preferred for suitable new stages without a mandatory speed win. File-level Arrow/Parquet interchange is sufficient. Data QC failure blocks analyses, not merely triggers warnings.
6. **After each analysis** perform N2, rechecking intervening publications, datasets, methods and journal relevance; record replicate/reframe/combine/stop decision without revising the frozen protocol. Perform N3 immediately before submission or transfer. At both pre- and post-analysis gates assess retaining, removing or replacing dependencies using [Ponytail language triage](../research/language-dependency-triage.md); do not introduce a package without an identified consumer, scientific oracle and evidence. Record actual commands/checks and distinguish completed initial intake from future analysis.
7. Use one source of policy: `edithatogo/repository-standards`. Adopt GitHub shared defaults and templates only when applicable. No second competing Conductor installation.
8. Local development acceptance uses the official GitHub Actions self-hosted runner on the relevant target OS/architecture, with a revision-bound observed run. Follow [local development](../research/local-development.md); no untrusted PR execution on personal machines, emulator substitution or unobserved success claim.
9. Before changing code and after each bounded increment, run `uv run --project tools/hf-release --frozen --python 3.15.2 python scripts/verify.py --deep`. Follow the [strict CI contract](../research/ci-plan.md) for initial tool installation, exact receipts, separate central privacy scanning and outstanding licence/provider/device gates. Missing or failed checks are not a pass. Preserve template patch/nonregression coverage policy and existing numerical tolerances.
10. Install the native pre-commit hook before the first implementation commit. Stage the complete candidate and let its central privacy/strict gates pass. A read-only hosted GitHub Actions replay may invoke the actual installed hook on a local commit of the exact current-base PR merge tree for an API-authored staging candidate. Require the observed hook/tree and current hosted checks before merge; this is not an owner-device receipt. Hugging Face is storage only. Follow [repository integration](../research/repository-integration.md): qualify and publish limma first, pin its actual commit in atlas, then run the receiving gate and atlas's own local/hosted checks. Keep one authoritative numerical specification and separate bounded receiving evidence.

### Medallion decision

**Approved:** logical Bronze (raw originals/rights/hash), Silver (qualified observations and ontology maps), Gold (published analysis tables/results). **Deferred:** a service-backed lakehouse, managed catalogues, orchestration, Fabric/Databricks/Delta/Iceberg, platinum layer, data warehouse schemas until materially needed.

Follow [hosting and resource decisions](../research/resources-hosting-reuse.md). Reuse the existing Hugging Face estate registry and eligible MONDO/Orphadata snapshots. Medallion promotion does not expand rights. The owner authorises the minimal GitHub–HF integration. Publish the API catalogue and eligible artifacts through a source-bound manifest. Record one artifact decision, reusing it for identical bytes; do not add a second human sign-off, new author permission or blanket ethics requirement unless an actual source or institutional condition requires it. Rights do not expand through transformation. Source-linked Bronze is sufficient; mirrored Bronze is optional and explicitly recorded.

### Publication boundaries

Check each journal's live aims, article categories, APC, indexing and policies at submission; scope fit is not acceptance likelihood. Avoid splitting one modest study into redundant publications.

Use the [experiment/publication plan](../research/experiment-publication-plan.md). E0/E2/E3 form the initial clinical bundle; E1 and backend comparisons ordinarily support it. E4–E6 are conditional extensions or a combined later study, not an automatic paper per track. If novelty overlaps, combine, reframe as justified replication, retain as infrastructure or stop. Added ontologies, Rust ports and Enzyme alone do not constitute clinical novelty.

### Track completion and archiving

The owner has chosen implement → review → archive. Once a bounded track passes its declared exit criteria, record the source/input hashes, commands and outcomes, independent Ponytail review and limitations, then move it to `conductor/archive/<track_id>/`. Remove it from the active track list and link it from `conductor/archive/README.md`. Do not archive a parent with unresolved scientific/device tasks. A completed infrastructure track may explicitly leave owner-device qualification in the existing device milestone. Timing estimates use agent batches; actual execution duration is recorded separately.
